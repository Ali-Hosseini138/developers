# اجرای مستقل پنل نت‌استور

کد پنل برای اجرا به Supabase، Vercel Blob یا Vercel Analytics نیاز ندارد. Next.js روی Node.js اجرا می‌شود؛ تا انتقال دامنه و استقرار روی سرور مقصد، سایت فعلی همچنان روی میزبان قبلی است. حذف وابستگی کد به معنی انجام انتقال زیرساخت نیست.

## مسیر داده‌ها

- ورود، نشست و پروفایل: JWT و پروفایل بک‌اند Django؛ هیچ حساب واسطی ساخته نمی‌شود. شناسه و پذیرش قوانین فقط از بک‌اند دریافت می‌شوند.
- اپ‌های توسعه‌دهنده، نسخه‌ها، بررسی، آمار و تیکت‌های جدید: APIهای Developer Hub.
- کاتالوگ عمومی: داده‌های آزمایشی قدیمی طبق درخواست مالک حذف می‌شوند؛ `data/public-catalog.json` خالی است. اپ‌های جدید خودکار به این کاتالوگ اضافه نمی‌شوند تا قرارداد API عمومی بک‌اند ارائه شود. فهرست «اپ‌های من» منبع کاتالوگ عمومی نیست.
- مسیر قدیمی `/api/blob-file` بازنشسته است و همیشه 404 می‌دهد. هیچ فایلی را از سرویس قبلی دریافت نمی‌کند.
- اطلاعات قدیمی Supabase و فایل‌های ذخیره‌شده قدیمی آزمایشی اعلام شده‌اند و نیاز به مهاجرت ندارند. پاک‌سازی پس از انتشار نسخه بدون وابستگی انجام می‌شود. پروژه میزبان فعلی تا انتقال DNS حذف نمی‌شود.


## پیش‌نیاز مسئول سرور و بک‌اند

1. سرور Linux دارای Docker/Compose، دامنه، DNS و HTTPS. دسترسی امن سرور را در سامانه استقرار ثبت کنید؛ رمز و کلید خصوصی را در چت یا مخزن نگذارید.
2. آدرس قطعی production بک‌اند: مشخص شود آدرس فعلی دارای `dev` مقصد تولید است یا خیر.
3. اجرای migrationهای `developer_hub`، کارگر پردازش APK، watchdog و ثبت زمان‌بندی‌شده آمار نصب. رفع خطای قبلی مهلت پرداخت با `USE_TZ=False` باید تأیید شود.
4. ذخیره فایل‌های جدید و دیتابیس بک‌اند باید مستقل از سرویس‌های قبلی باشد؛ تنها از ظاهر URL فایل نمی‌توان محل واقعی ذخیره را تأیید کرد.
5. لینک‌های تأیید ایمیل و بازیابی رمز روی دامنه نهایی تنظیم شوند. callback قدیمی دارای code نشست جدید نمی‌سازد و کاربر را برای درخواست لینک تازه هدایت می‌کند.
6. طبق دستور مالک، داده‌های آزمایشی قبلی به Django منتقل نمی‌شوند. حساب‌ها و اپ‌های واقعی از مسیرهای جدید ثبت شوند؛ پذیرش قوانین در ثبت‌نام بک‌اند ثبت می‌شود.
7. API عمومی فهرست/جزئیات اپ‌ها و روش به‌روزرسانی کاتالوگ عمومی باید مشخص شود؛ قرارداد چنین APIای در فایل‌های فعلی نبود.

## تنظیم و اجرا

از ریشه مخزن:

```sh
cp deploy/selfhost.env.example .env.selfhost.local
chmod 600 .env.selfhost.local
```

`DEVELOPER_API_BASE_URL` باید HTTPS origin بدون مسیر و اسلش پایانی باشد و در build و runtime یکسان بماند. مقدار `RELEASE_TAG` را به SHA انتشار تغییر دهید. هیچ کلید Supabase، Blob یا کلید امضای هویت واسط لازم نیست. توکن‌های کاربران در کوکی HttpOnly نگهداری می‌شوند.

```sh
docker compose --env-file .env.selfhost.local -f deploy/compose.yaml config --quiet
docker compose --env-file .env.selfhost.local -f deploy/compose.yaml build app
docker compose --env-file .env.selfhost.local -f deploy/compose.yaml up -d
docker compose --env-file .env.selfhost.local -f deploy/compose.yaml exec proxy nginx -t
curl --fail http://127.0.0.1:8080/api/health
```

API سلامت فقط زنده‌بودن پردازش Next را نشان می‌دهد، نه سلامت بک‌اند. image، دیتابیس، storage و تنظیمات محرمانه باید جداگانه پشتیبان داشته باشند. build بسته‌های npm و فونت‌ها را دریافت می‌کند؛ برای سرور بدون اینترنت، image را در محیط build بسازید و منتقل کنید. فونت‌های ساخته‌شده در زمان اجرا از خود سایت سرو می‌شوند.

پراکسی HTTPS عمومی درخواست‌ها را به `127.0.0.1:8080` بفرستد و `Host` و `X-Forwarded-Proto: https` را تنظیم کند. پورت داخلی اپ عمومی نشود. سقف کل درخواست حداقل ۴۰۰ MiB، timeout حداقل ۶۵۰ ثانیه و buffering آپلود خاموش باشد؛ خود بک‌اند نیز باید APK تا ۳۰۰ مگابایت به‌علاوه تصاویر را بپذیرد. مسیر `/backend-api/` با حفظ اسلش نهایی، Authorization، query و بدنه به بک‌اند می‌رود. درخواست تغییردهنده خودکار تکرار نمی‌شود.

### به‌روزرسانی کاتالوگ مستقل

به‌صورت پیش‌فرض کاتالوگ بسته‌شده با برنامه خوانده می‌شود. برای تغییر بدون build مجدد می‌توان فایل JSON مستقل حاوی `updatedAt` و آرایه `apps` با قرارداد `StoreApp` را به کانتینر mount کرد و `PUBLIC_CATALOG_FILE` را به مسیر داخل کانتینر تنظیم کرد. تنها اپ‌های دارای `status: published` مجازند؛ فایل نادرست خطا می‌دهد و به سرویس قدیمی برنمی‌گردد. فایل به‌صورت atomic تعویض شود. تنظیم mount بر عهده مسئول استقرار است.

## انتقال و آزمون پذیرش

قبل از تغییر DNS، با همان دامنه و HTTPS روی سرور جدید تست کنید: ثبت‌نام و تأیید ایمیل، ورود و تمدید نشست، خروج، پروفایل، فهرست اپ‌ها، ویرایش، آپلود واقعی، پردازش APK، آمار و اکسل، تیکت و بررسی ادمین. درخواست‌های دامنه‌های Supabase و Vercel را در محیط آزمایش مسدود کنید و همین مسیرها را دوباره بررسی کنید. تست روی بک‌اند شبیه‌سازی‌شده جای تست production را نمی‌گیرد.

پس از تأیید، DNS دامنه اصلی به سرور جدید منتقل شود. داده‌های آزمایشی قدیمی پس از انتشار نسخه مستقل قابل پاک‌سازی‌اند؛ خود میزبانی فعلی تا تأیید سرور مقصد حفظ شود. rollback با بازگرداندن DNS یا image قبلی انجام می‌شود؛ rollback برنامه، دیتابیس و تنظیمات را برنمی‌گرداند. پس از recreate اپ، proxy را restart کنید.

## پشتیبان

```sh
sh scripts/backup-source.sh /PRIVATE_BACKUP_DIRECTORY
```

پشتیبان کد شامل دیتابیس، فایل خصوصی و اسرار runtime نیست. برای داده‌های واقعی جدید، نسخه‌های پشتیبان خصوصی باید روی storage مستقل از سرور اصلی و با کنترل دسترسی نگهداری شوند. بازیابی آزمایشی لازم است.
