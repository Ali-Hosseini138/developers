# اجرای مستقل پنل نت‌استور

این بسته امکان اجرای صفحات، APIهای Next.js و پراکسی آپلود را خارج از Vercel فراهم می‌کند. افزودن این فایل‌ها به‌تنهایی میزبان سایت را تغییر نمی‌دهد. مسیر فعلی Vercel تا زمان انتقال دامنه فعال می‌ماند. خروجی HTML استاتیک برای این پروژه کافی نیست: ورود، کوکی‌ها، پروفایل و APIهای واسط نیاز به پردازش سمت سرور دارند.

## اجزا و وابستگی‌های باقی‌مانده

| جزء | پس از اجرای این بسته |
| --- | --- |
| صفحات، ورود توسعه‌دهنده و مدیریت، APIهای واسط | Node.js روی سرور جدید |
| آپلود APK و تصاویر | nginx روی سرور جدید → بک‌اند Django؛ بدون عبور از Vercel |
| حساب‌ها، اپ‌ها، نسخه‌ها، بررسی انتشار، تیکت و آمار | بک‌اند فعلی؛ انتقال فرانت جای آن را عوض نمی‌کند |
| پروفایل، پذیرش قوانین و اتصال هویت در ورود | همچنان Supabase؛ قطع آن بدون مهاجرت داده/API باعث اختلال ورود و پروفایل می‌شود |
| خواندن فایل‌های قدیمی `/api/blob-file` | همچنان Vercel Blob، اگر داده قدیمی وجود داشته باشد؛ موجودی هنوز تأیید نشده |
| آمار بازدید Vercel | در ایمیج مستقل خاموش؛ آمار نصب اپ از بک‌اند مستقل از این تنظیم است |

## موارد لازم از مسئول سرور و بک‌اند

1. **سرور مقصد و دامنه:** دسترسی امن مسئول استقرار به سرور Linux دارای Docker Engine و Compose v2، خروجی اینترنت به بک‌اند/Supabase، کنترل DNS و گواهی HTTPS دامنه. پورت 8080 این بسته فقط روی localhost باز می‌شود و باید پشت پراکسی HTTPS سرور قرار بگیرد. رمز، SSH private key و توکن را در چت نفرستید؛ در محل امن استقرار ثبت کنید.
2. **آدرس پایدار محیط production:** مشخص شود `https://macil.dev.netboxteam.com` واقعاً مقصد تولید است یا محیط توسعه. آدرس نهایی، بدون path و اسلش آخر، در `DEVELOPER_API_BASE_URL` ثبت شود. دسترسی از IP سرور مقصد، DNS، TLS و عدم ریدایرکت POST/PATCH بررسی شود. در مدل same-origin این بسته، صرفاً برای مرورگر نیازی به بازکردن CORS عمومی نیست.
3. **آپلود:** کل زنجیره تا وب‌سرور Django باید APK تا ۳۰۰ مگابایت به‌علاوه سایر بخش‌های multipart را بپذیرد. پراکسی این بسته سقف کل درخواست ۴۰۰ MiB و timeout آپلود ۶۵۰ ثانیه دارد؛ timeout مرورگر فعلی ۱۰ دقیقه است. TLS proxy بیرونی و بک‌اند نباید سقف پایین‌تری داشته باشند. مسیر `/backend-api/api/v1/developer-hub/apps/` باید با اسلش نهایی به `/api/v1/developer-hub/apps/` برسد؛ Authorization، query و body باید حفظ شوند. درخواست تغییردهنده نباید خودکار تکرار شود.
4. **پروفایل و قوانین برای حذف وابستگی Supabase:** قرارداد خواندن/ویرایش نام، تلفن، کد ملی، سازمان و وضعیت/زمان پذیرش قوانین و یک شناسه پایدار حساب لازم است. ابتدا نگاشت و مهاجرت پروفایل‌های موجود به حساب Django و سپس اصلاح ورود انجام شود. این endpointها هنوز در این بسته ساخته یا فرض نشده‌اند. تا آن زمان همان پروژه Supabase و کلیدهای فعلی حفظ شوند.
5. **فایل و پشتیبان:** مالک و محل واقعی ذخیره APK/تصاویر جدید، روش نسخه پشتیبان و بازیابی، و اعتبار URLهای فایل بعد از انتقال روشن شود. برای Blob قدیمی، موجودی مسیرهای `users/` با ارجاع‌های `icon_path`، `banner_path` و `screenshot_paths` تطبیق داده شود؛ فایل‌های دارای ارجاع به storage مقصد منتقل و ارجاع‌ها با حفظ کنترل دسترسی اصلاح شوند. کلید Blob فقط پل موقت است و استقلال کامل ایجاد نمی‌کند. این بسته هیچ فایل یا رکوردی را حذف نمی‌کند.
6. **ورود و ایمیل:** URL بازگشت تأیید ایمیل و بازیابی رمز در سرویس ایمیل/احراز هویت به دامنه اصلی نهایی اشاره کند. با حفظ دامنه و همان کلید امضای هویت، کوکی‌ها امکان تداوم دارند؛ تغییر دامنه یا کلید می‌تواند ورود دوباره بخواهد. کلیدهای سرور فقط به runtime منتقل شوند.
7. **اصلاحات شناخته‌شده بک‌اند:** خطای ثبت‌شده مهلت پرداخت در استفاده از `timezone.localdate()` با `USE_TZ=False` در Django باید رفع و تست شود. دسترس‌پذیری بک‌اند از سرور جدید هم بررسی شود؛ جابه‌جایی فرانت به‌تنهایی رفع timeout ارتباط با سرویس ورود را تضمین نمی‌کند. تیکت فعلی سؤال/پاسخ محدود دارد؛ ادامه گفتگو، پاسخ مجدد توسعه‌دهنده و بستن/بازگشایی نیاز به قرارداد بک‌اند جداگانه دارد.

## آماده‌سازی امن تنظیمات

از ریشه مخزن:

```sh
cp deploy/selfhost.env.example .env.selfhost.local
chmod 600 .env.selfhost.local
```

مسئول استقرار مقادیر را در همین فایل یا مخزن امن تنظیمات ثبت کند. فایل فوق از Git و build context داکر حذف شده است. مقدار `RELEASE_TAG` باید پیش از هر build برچسب یکتای همان انتشار، مثلاً SHA کامیت، باشد. خروجی `docker compose config` ممکن است اسرار را نشان دهد؛ برای بررسی فقط `config --quiet` استفاده کنید.

`NEXT_PUBLIC_SUPABASE_URL` و کلید عمومی Supabase در build وارد فایل مرورگر می‌شوند؛ تغییرشان نیاز به build مجدد دارد. `DEVELOPER_API_BASE_URL` در بازنویسی Next هم در build ثبت می‌شود و باید با مقدار runtime و nginx یکسان باشد. تغییر مقصد بک‌اند نیاز به build مجدد و بازسازی proxy دارد. `SUPABASE_SERVICE_ROLE_KEY` و `DEVELOPER_SESSION_SIGNING_SECRET` فقط runtime هستند و نباید build argument باشند. اگر در تولید کلید امضای مستقل وجود ندارد، همان service-role فعلی به‌عنوان fallback حفظ شود؛ افزودن کلید تازه هم‌زمان با انتقال، نشست‌های قدیمی را بی‌اعتبار می‌کند.

## build و راه‌اندازی

```sh
docker compose --env-file .env.selfhost.local -f deploy/compose.yaml config --quiet
docker compose --env-file .env.selfhost.local -f deploy/compose.yaml build app
docker compose --env-file .env.selfhost.local -f deploy/compose.yaml up -d
docker compose --env-file .env.selfhost.local -f deploy/compose.yaml exec proxy nginx -t
curl --fail http://127.0.0.1:8080/api/health
```

این health فقط زنده بودن پردازش Next را نشان می‌دهد؛ سلامت بک‌اند، ورود، Supabase و فایل‌ها باید جداگانه تست شوند. build برای دریافت بسته‌های npm و فونت‌های Google به دسترسی شبکه نیاز دارد؛ فونت خروجی در سایت به‌صورت محلی سرو می‌شود. برای محیط محدود، ایمیج را در ماشین build قابل‌اعتماد بسازید و در registry خصوصی یا با `docker save`/`docker load` به مقصد برسانید. ایمیج و dependencyها باید به‌صورت دوره‌ای به‌روزرسانی و اسکن شوند؛ برچسب `nginx:stable-alpine` به digest ثابت در زیرساخت نهایی تبدیل شود.

پراکسی عمومی HTTPS روی خود سرور باید درخواست‌ها را به `127.0.0.1:8080` برساند؛ Host اصلی و `X-Forwarded-Proto: https` را خودش تنظیم کند؛ سقف body حداقل ۴۰۰ MiB، timeout حداقل ۶۵۰ ثانیه و request buffering خاموش داشته باشد. در تنظیمات nginx این proxy بیرونی:

```nginx
location / {
    client_max_body_size 400m;
    client_body_timeout 650s;
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto https;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_request_buffering off;
    proxy_buffering off;
    proxy_send_timeout 650s;
    proxy_read_timeout 650s;
}
```

این قطعه باید داخل server موجود با TLS معتبر قرار گیرد؛ به‌تنهایی فایل nginx کامل نیست. پورت داخلی اپ را عمومی نکنید. کوکی ورود در production امن است و تست ورود واقعی باید روی HTTPS انجام شود.

## انتقال و بازگشت

قبل از تغییر DNS، دامنه نهایی را فقط روی دستگاه تست به IP مقصد نگاشت کنید تا HTTPS، ورود و کوکی‌ها با همان دامنه واقعی بررسی شوند. با حساب تست، ورود توسعه‌دهنده/مدیر، فهرست و ویرایش اپ، پروفایل و قوانین، آپلود واقعی تا سقف مجاز، تیکت، خروجی اکسل، تأیید ایمیل و بازیابی رمز را بررسی کنید. یک فایل قدیمی و یک فایل جدید نیز باز شود. در Network مرورگر نباید رفتن به دامنه‌های Vercel برای کار اصلی سایت باقی مانده باشد؛ مسیر Blob قدیمی تا مهاجرت فایل‌ها استثنای شناخته‌شده است.

پس از تأیید، DNS دامنه اصلی به سرور جدید تغییر کند. Vercel را تا پایان دوره مشاهده و اطمینان از مهاجرت فایل‌ها حذف نکنید. در صورت ایراد، DNS به مقصد قبلی بازگردد و همان بک‌اند/دیتابیس حفظ شود تا داده‌ها دوشاخه نشوند. انتشار Docker تک‌نمونه‌ای است؛ `up` ممکن است وقفه کوتاه داشته باشد و انتشار بدون وقفه نیاز به دو نمونه و load balancer دارد.

برای rollback نسخه برنامه، ایمیج قبلی را نگه دارید، `RELEASE_TAG` را به نسخه قبلی برگردانید و `up -d --no-build` اجرا کنید. این کار rollback دیتابیس یا تنظیمات نیست؛ snapshot امن تنظیمات هر انتشار نیز لازم است. پس از recreate اپ، proxy را restart کنید تا IP داخلی app را دوباره resolve کند. پس از تغییر DNS بک‌اند هم proxy را restart کنید. ایمیج قبلی را تا تأیید نسخه تازه پاک نکنید.

## پشتیبان و آزمون بازیابی

```sh
sh scripts/backup-source.sh /PRIVATE_BACKUP_DIRECTORY
```

اسکریپت از تاریخچه کامیت‌شده HEAD یک Git bundle می‌سازد، با `git bundle verify` بررسی و SHA256 ثبت می‌کند. تغییرات commit‌نشده، env، دیتابیس و فایل کاربران در این بسته نیستند. آن را به ذخیره‌سازی خصوصی مستقل از میزبان منتقل کنید. بازیابی کد با `git clone /path/to/netstore-....bundle recovered` قابل آزمون است.

بک‌اند باید جداگانه backup زمان‌بندی‌شده دیتابیس و storage، نگهداری خارج از سرور اصلی و آزمون restore در محیط ایزوله داشته باشد. اسرار runtime، تنظیمات DNS/TLS و ایمیج قابل‌اجرای هر انتشار هم در محل امن نگهداری شوند. زمان قابل‌قبول از‌دست‌رفتن داده و زمان بازیابی را مالک سرویس تعیین کند. داشتن کپی GitHub به‌تنهایی پشتیبان اطلاعات کاربران نیست.

## مرز اعتبارسنجی

دستورات build و smoke test محلی باید در گزارش هر تغییر ثبت شوند. تا زمانی که Docker و سرور مقصد، تنظیمات واقعی و حساب تست در اختیار مسئول استقرار نباشند، اجرای کانتینر، nginx، آپلود ۳۰۰ مگابایتی، بازیابی داده و قطع کامل Vercel تأیید‌شده محسوب نمی‌شوند.
